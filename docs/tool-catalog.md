# Embedded tool catalog

The embedded catalog contains **221 tool manifests and 18 profiles**. The complete, current list is available from `go run ./cmd/bootstrap catalog`; `go run ./cmd/bootstrap catalog --json` emits the manifest data as JSON. Source manifests are in `internal/catalog/data/tools/`, and profiles are in `internal/catalog/data/profiles/`.

The catalog covers version control, JavaScript and TypeScript, JVM, C and C++, Python, Go, Rust, .NET, PHP, Ruby, Swift, Dart and Flutter, Zig, Lua, BEAM, Haskell, OCaml, Clojure, Julia, R, Perl, Fortran, additional languages, mobile and embedded development, database clients, API and protocol tooling, containers and DevOps, security and code quality, and documentation utilities.

The 18 editable profiles are Additional languages, API and protocol tooling, Complete catalog, Database clients, DevOps tooling, .NET development, Embedded development, Essential, Full-stack, Go, Java, Mobile development, Python, Rust, Security and code quality, Swift, Systems programming, and Web development. Applying a profile changes the selection; it does not execute an installation.

## Manifest and installer model

Manifests declare tool IDs, version channels, no-automatic-upgrade policy, executables and version arguments, common and platform-specific dependencies, conflicts, supported platforms, and compatible installer methods. Installer methods include existing OS package managers, exact-version npm/PyPI/Go/Cargo registry entries, and catalog-pinned direct archives. Direct archives may include size limits, digest-verified regional URLs, expected archive roots, version markers, PATH entries, user-visible setup actions, and installation disclosures. Manifests cannot contain arbitrary shell fragments.

The runtime loader uses typed Go structures and strict YAML decoding. It rejects unknown fields, invalid manager/platform/scope combinations, malformed artifact metadata, duplicate IDs, missing dependencies, dependency cycles, and any declared OS/architecture without a matching installer route. It also checks that each dependency supports the same OS/architecture and that each declared platform alternative exists on every architecture it names. `go run ./cmd/catalog-check` validates the embedded catalog and profiles; add `-matrix` to see exact install routes, disclosed native alternatives, and uncovered OS/architecture pairs for Windows, macOS, and Linux. A declared package route is not a claim that every package-manager version has been live-tested; see [platform support](platform-support.md).

## Availability and verification

An install route must exist for each declared OS/architecture, but its package manager still has to be installed and configured on the user's machine. Direct archive and registry methods are limited to the exact platform and tool entries in each manifest. A plan reports the chosen source, command, integrity digest, install target, and any persistent PATH change before approval.

CI exercises native builds on Windows, macOS, and Linux amd64/arm64. The package-manager workflow covers Ninja through APT, DNF, YUM, Pacman, Zypper, APK, and FreeBSD `pkg`; SQLite through Chocolatey; 7-Zip through WinGet and Scoop on Windows amd64; and OpenOCD through Homebrew on macOS amd64 and arm64. Other declared manager/tool pairs are not claimed as live integration-tested. See [platform support](platform-support.md) for the current matrix.

Recently audited package sources include Bun through the [upstream Homebrew tap](https://github.com/oven-sh/homebrew-bun/blob/main/Formula/bun.rb), .NET 10 and Zig through [Homebrew's Linux bottles](https://formulae.brew.sh/formula/dotnet) and [Zig formula](https://formulae.brew.sh/formula/zig), GitHub CLI through its [FreeBSD `pkg` instructions](https://github.com/cli/cli/blob/trunk/docs/install_linux.md#freebsd), OpenSSH through the [Scoop manifest](https://github.com/ScoopInstaller/Main/blob/master/bucket/openssh.json), [MacPorts port](https://ports.macports.org/port/openssh/details/), and [FreeBSD port package](https://www.freshports.org/security/openssh-portable/), PowerShell through the [official release archive and SHA-256 list](https://github.com/PowerShell/PowerShell/releases), and Flutter through Google's [Windows](https://storage.googleapis.com/flutter_infra_release/releases/releases_windows.json) and [Linux](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json) release manifests. These are source references; the CI matrix does not yet exercise every listed tool and manager combination.

When adding a manifest, verify each package identifier and source against maintained upstream or package-manager metadata, check publisher and scope, declare only tested platform mappings, update relevant profiles, add focused validation coverage, and run the catalog checker.
